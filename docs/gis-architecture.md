# Pravah V2 — GIS & Ward Data Architecture (Phase 1C)

This document details the geospatial architecture, coordinate systems, spatial indexing, and spatial query operations implemented in Pravah V2.

---

## 1. Spatial Coordinate Reference System (CRS)

Pravah V2 standardizes exclusively on **EPSG:4326** (WGS 84):
- **Axis Order**: Longitude (X), Latitude (Y)
- **Unit**: Decimal Degrees
- **Bounding Box for Delhi NCR**:
  - Latitude: `28.35° N` to `28.95° N`
  - Longitude: `76.80° E` to `77.45° E`

All spatial points and polygons are created using `ST_SetSRID(..., 4326)`. For metric distance calculations (e.g. radius searches in meters), coordinates are cast to PostGIS `geography` types (`location::geography`).

---

## 2. Geometry Types & Storage

| Entity | Field | PostGIS Type | Representation |
| :--- | :--- | :--- | :--- |
| **Ward** | `boundary` | `geometry(MultiPolygon, 4326)` | Full boundary polygon of the ward |
| **Complaint** | `location` | `geometry(Point, 4326)` | Precise coordinates where waterlogging is reported |
| **Incident** | `location` | `geometry(Point, 4326)` | Operational flood incident centroid/point |
| **Infrastructure** | `location` | `geometry(Point, 4326)` | Asset coordinate (pump, drain outfall, underpass) |
| **ResponseTeam** | `current_location` | `geometry(Point, 4326)` | Real-time GPS coordinate of the response unit |

---

## 3. Spatial Indexes

PostGIS Generalized Search Tree (**GiST**) indexes are created on every geometry column:
```sql
CREATE INDEX idx_wards_boundary ON wards USING GIST (boundary);
CREATE INDEX idx_complaints_location ON complaints USING GIST (location);
CREATE INDEX idx_incidents_location ON incidents USING GIST (location);
CREATE INDEX idx_infrastructure_location ON infrastructure USING GIST (location);
```

GiST indexes provide logarithmic bounding box search times (`O(log N)`), ensuring instant spatial lookups even across hundreds of thousands of incident points.

## 4. Key Spatial Workflows

### A. Point-in-Polygon Ward Resolution
When a citizen reports a complaint at `(lon, lat)`, the system automatically resolves which municipal ward contains that point:

```sql
SELECT id, ward_code, ward_name
FROM wards
WHERE boundary IS NOT NULL
  AND ST_Contains(boundary, ST_SetSRID(ST_MakePoint($lon, $lat), 4326))
LIMIT 1;
```

If a point falls slightly outside administrative boundaries (e.g. boundary edge error), the system falls back to nearest-ward proximity:

```sql
SELECT id, ward_code, ward_name
FROM wards
ORDER BY boundary <-> ST_SetSRID(ST_MakePoint($lon, $lat), 4326)
LIMIT 1;
```

### B. Proximity Dispatch & Asset Search
To find operational emergency pumps within 2,000 meters of an active flood incident:

```sql
SELECT id, name, type, ST_Distance(location::geography, $incident_point::geography) AS distance_meters
FROM infrastructure
WHERE type = 'PUMP_STATION'
  AND status = 'OPERATIONAL'
  AND ST_DWithin(location::geography, $incident_point::geography, 2000)
ORDER BY distance_meters ASC;
```

## 5. Boundary Data Lineage & Synthetic Flagging

Per project rules, synthetic geometry must never be presented as official data:
1. **Source**: V1 provided centroid points (`latitude, longitude`) for 250 Delhi municipal wards in `backend/data/wards.csv`.
2. **Current Development Data**: Standardized `MultiPolygon` geometries are generated by `server/src/scripts/generate-demo-boundaries.js` and stored in `server/data/demo-ward-boundaries.json`.
3. **Explicit Tagging**: All demo records carry:
   ```json
   {
     "is_synthetic": true,
     "source": "derived-hexagon-demo-v2",
     "note": "Demo geometries for development. Ready to be replaced by official MCD boundary GeoJSON."
   }
   ```
4. **Upgrading to Official GeoJSON**: When official MCD delimitation shapefiles/GeoJSON are ingested, the ingestion script will replace these boundaries and set `is_synthetic: false`.
